# Long-wait 积压消息集中回应

2026-10-11，用户要求恢复监听后不再逐条补答旧招呼，而是读完积压内容后集中回应。

## 行为

- `cove_bridge_wait` 自动识别积压：队首主人消息已等待至少 60 秒，且有至少两条连续、未投递的同房间同发送者消息。
- 一批最多 32 条、原文加上下文合计 64,000 字符。超过上限的消息仍在队列里，后续继续处理；不截断原文。
- 完整原文、时间和原始上下文按 FIFO 返回。模型应一起读，回答仍然相关的问题和最新意图，不逐条补答过时招呼或测试。后来的取消/更正优先，不盲目执行旧命令。
- 同批只调用一次 `cove_bridge_reply`（可以有多个短气泡）。这不等于保证模型一定遵循表达风格；需在实际宿主继续验收。
- 普通新消息、单条消息、无可靠房间/发送者标识的消息仍走原有流程。其他成员消息和房间/发送者边界会分批，因此大量交错的多人消息可能产生多次集中回应。

## 协议与不变量

这是 conversation「每事件单独 required reply」的明确、局部设计调整，不是 latest-state-wins，也没有删除或替换原始事件。

批首原始 eventId 作为批身份，返回新增可选字段 `batchEventIds`。所有成员一并 reserved；ACK 批首 id 后一并 delivered。已接受的批不能 release 回 pending。交付前取消可原子 release 整批。不能用成员 id 单独 ACK、claim 或 release，也不能用 Widget dismissed 跳过此批。

所有成员共享一份 fingerprint/sentCount/completed 回复日志，回复完成前继续阻塞下一批。中途断线从已发送气泡之后恢复，完成后相同回复重试不重复发送。新到消息不并入已投递的批。原始 eventId、正文及入队去重记录继续保留。

房间/发送者键由 NetEase adapter 传递，不能从用户正文推断。不同 source、replyRoute、room/sender 不混批，profile filter 仍生效。Widget 仍单条投递，禁止与 long-wait 同时消费。

## 更新与验证

更新代码、build、重启音乐服务后自动生效，不需要重建插件或重启 OAuth 网关。已发布工具 schema 可刷新；旧 schema 不阻止处理文本中的批契约。

回归覆盖：顺序与原文保留、ACK 重试、集中回复中途失败/恢复/去重、backpressure、交付前 release、接受后不重放、来源和房间边界、数量及长度上限。实际验收：暂停监听一分钟并积压两条以上主人消息，再恢复，应收到一次集中回应。

仍为内存队列。服务重启会丢失尚未消费的积压；这次没有实现持久化或永久后台监听。

## 过期消息与歌词去重（Claude，2026-10-12）

- 监听（Long-wait 或 Widget）开始取事件时，`createdAt` 超过 `BRIDGE_STALE_EVENT_SECONDS`（默认 300 秒，0 = 关闭）的
  conversation / state 事件直接标记为已送达：不交给模型，必须回复的事件记为「已跳过」，不再占着回复的 backpressure。
  已被取走、或正在回复中的事件不受影响。
- 跳过的条数和时间范围写进日志（不含消息文字）；下一次 `cove_bridge_wait` 返回时附带 `skippedStale` 和一句摘要，
  例如「已跳过 12 条超过 5 分钟的旧消息」。
- 顺序：先跳过过期的，剩下 1～5 分钟内同一房间同一发送人的积压，照上面的规则合并成一次回复。
- 同一首歌的完整歌词只在第一次（一般是换歌事件）附带一次；之后同一首歌的聊天 / 播放事件只带一句说明，
  需要附近歌词时调用 `netease_together_now`。
